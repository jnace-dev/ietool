# IE 快捷方式创建工具（Windows 10 / Windows 11）

一个单文件 exe：在 Windows 10 / Windows 11 上创建“启动 Internet Explorer”的桌面 / 开始菜单快捷方式。
默认生成的快捷方式等价于执行：

```
"C:\Program Files\Internet Explorer\iexplore.exe" https://www.baidu.com/#ie= -Embedding
```

默认快捷方式名是 **`IE`**（缩写），可以直接在界面上的“快捷方式名”里改成任意名字——
**工具不会再自动改名**，就用你填的名字。

## 文件说明

| 文件 | 说明 |
| --- | --- |
| `dist\ie_launcher.exe` | **成品**，单文件约 13 MB，目标机无需安装 Python |
| `ie_launcher.py` | 源码（tkinter 图形界面 + 命令行双模式，Python 3.8+） |
| `ie_launcher.spec` | PyInstaller 打包配置 |
| `ie_launcher.manifest` | exe 清单：声明 DPI 感知（Per-Monitor V2）与长路径支持 |
| `ie_icon.ico` / `ie_png.png` | IE 图标资源（exe 图标；也可作为快捷方式图标） |
| `tests\` | 回归自测脚本（九个，用 `.venv\Scripts\python tests\xxx.py` 跑） |

## 核心原则：界面参数就是唯一来源

界面上的每一项都会原样写进快捷方式，创建后立即读回来逐项核对，有任何一项没写进去都会明确报出来：

- **实际生效的命令** 预览区实时显示即将执行的完整命令行与保存路径（改任何输入框都会立刻刷新）。预览和真正创建走的是同一套 `plan_shortcut()` 规则，所以“预览里看到的”就是“真正写进去的”。
- 创建成功后，日志逐行给出 `√/×` 核对结果：目标程序 / 启动参数 / 工作目录 / 图标 / 描述 / 快捷方式名 / 保存位置，共 7 项。
- 自定义目录**填了就生效**：在目录框里输入路径会自动把“创建位置”切到“自定义目录”，不存在“填了却被忽略”的情况；清空后也不会静默回退，而是提示“自定义目录还没填写目录”。
- 图标来源有两种：`system`（用目标程序自带的图标，默认）与 `bundled`（用工具内置的 IE 图标），按界面选择写入。
- “测试启动”用 `CommandLineToArgvW` 按 Windows 规则解析命令行，与快捷方式实际执行方式完全一致（带引号的参数不会被按空格切开）。
- 被安全软件拦截时，图形界面会**弹窗询问**是否改存到开始菜单并自动重试；命令行用 `--fallback-startmenu`。不会悄悄换一个位置了事。
- **快捷方式名就用界面上填的名字**（默认 `IE`），不做任何自动改名；只有在首选名字被安全软件按名字拦下时才会退到备选，并在日志里说明。

## 按“系统默认的属性”创建

落盘的 `.lnk` 与 Windows 自己生成的完全一致，避免杀软对“外部塞进来的快捷方式”的启发式误报：

- 优先走**系统外壳 API**（`WScript.Shell`）在目标目录直接创建，文件由系统生成，格式与系统无差别；
- 目标目录禁止 COM 新建时（安全软件拦截），改为**临时目录让系统生成一份，再把原始字节搬到目标目录**，
  搬完把文件属性整理成系统默认的样子：
  - 外部文件的创建/写入/访问时间 = 实际创建时刻（覆盖旧文件时也会刷新，不会留下旧时间）；
  - 文件属性 = `ARCHIVE (0x20)`；
  - 内嵌 ShellLinkHeader 里的三个时间戳保持不动——那是**目标程序**的时间戳，系统生成的快捷方式本来就是这样。

实测三处（开始菜单 / 当前用户桌面 / 所有用户桌面）落盘后：
外部 `mtime == ctime == 创建时刻`、属性 `0x20`、内嵌时间戳等于 `iexplore.exe` 的时间戳，
与系统原生生成的快捷方式逐项一致。

字节级实测（`IE.lnk`，2110 字节）：

```
HeaderSize = 0x4C            （MS-SHLLINK 规范值，布局没错位）
FileAttributes(头内) = 0x20  （ARCHIVE）
CreationTime  @0x1C = 133898436501772401  → 2025-04-23  = iexplore.exe 的时间戳
WriteTime     @0x2C = 133898436501913615  → 2025-04-23  = iexplore.exe 的时间戳
AccessTime    @0x24 = 1794796191.7        → 本次创建时刻（外壳写入）
```

也就是说：**内嵌的创建/写入时间就是目标程序自己的时间戳**，这是 Windows 自己生成快捷方式时的固有行为，
不是工具写歪了；工具只负责让**文件本身**的属性和时间戳看起来"就是刚被系统正常创建出来的"。

## 图形界面

双击 `ie_launcher.exe`：

- **环境检测**：系统版本、当前显示缩放（百分比 / DPI）、IE 程序路径、Edge 路径、真实桌面 / 开始菜单目录（自动识别 OneDrive、目录重定向）
- **快捷方式设置**：目标程序、启动参数、名称、描述、创建位置（桌面／开始菜单／所有用户桌面／所有用户开始菜单／自定义目录）、图标来源
- **操作**：创建快捷方式 / 测试启动 / 删除快捷方式 / 打开所在文件夹
- **测试启动**会真实拉起浏览器，并以窗口类 `IEFrame` 判断“是不是真的 IE”，给出真 IE / 被 Edge 接管的明确结论

### IE 位数互切按钮

目标程序右侧那个按钮的**文案跟着目标路径走**，点一下就切到另一种位数：

| 当前目标程序 | 按钮显示 | 点一下之后 |
| --- | --- | --- |
| `C:\Program Files\Internet Explorer\iexplore.exe`（64 位） | **用 32 位 IE** | 换成 `Program Files (x86)\…\iexplore.exe` |
| `C:\Program Files (x86)\Internet Explorer\iexplore.exe`（32 位） | **用 64 位 IE** | 换成 `Program Files\…\iexplore.exe` |
| 不是 IE 路径 | 切换 IE 位数 | 按本机实际存在的那个来定 |

位数判断规则：`Program Files` → 64 位，`Program Files (x86)` / `SysWOW64` → 32 位，`System32` → 64 位（64 位系统上）；手动输入其它路径时按“都不是”处理。

## DPI 缩放适配

界面在 100% / 125% / 150% / 200% 下都能正常显示：**文字清晰不虚、布局不重叠、整窗不超出屏幕**。
环境检测面板里也会显示当前缩放：`显示缩放 : 125%（120 DPI，已由 exe 清单声明）`。

### 三层做法

| 层次 | 做法 | 效果 |
| --- | --- | --- |
| 进程 | 建窗口**之前**调用 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`；exe 清单里也声明了 `PerMonitorV2` | 系统不再把窗口按位图整体拉伸，文字是重新渲染的，不再发虚 |
| 排版 | 按显示器真实 DPI 设置 Tk 的 `tk scaling`，并把界面里所有以**像素**为单位的外边距 / 内边距 / 换行宽度按同一系数换算 | 字号与留白跟着缩放比例一起变大，125% 下不会挤成一团 |
| 兜底 | 窗口放不下时先压缩文本行数、再整体缩小；窗口拖到缩放比例不同的显示器时自动重排 | 小屏上整窗完整可见，跨屏拖动不错位 |

### 踩过的坑：Tk 的 `tk scaling` 对已建控件无效

`tk scaling` 只在**新建字体**时把“磅”换算成像素，运行中改它**不会**重排已经建好的控件
（实测：`tk scaling` 从 1.668 改到 0.933，控件尺寸纹丝不动）。
所以自适应缩放（小屏兜底、跨屏重排）不能只改 `tk scaling`，
必须自己把字号换算成**像素**（Tk 里负数字号即像素）再写回控件——
`DpiLayout.apply_fonts()` 干的就是这件事，ttk 用的 `TkDefaultFont` 也要一起改。

另一个坑：`tkfont.nametofont()` 绑定的是“默认根窗口”，多窗口时可能作用到别的解释器上，
所以默认字体统一用 `root.tk.call("font", "configure", ...)` 直接改。

### 实测（1920×1080 显示器，系统缩放 125%）

```
进程 DPI 感知        : Per-Monitor V2（源码运行）/ 已由 exe 清单声明（打包后）
窗口 DPI             : 120  →  缩放系数 1.25
窗口尺寸             : 938 × 932，完整落在 1920 × 1030 的工作区内
打包后 GetDpiForWindow: 120
```

`tests\test_dpi_scale.py` 盯着这一整套行为。

## 命令行

```bat
ie_launcher.exe --create --location desktop --name "IE"
```

| 参数 | 说明 |
| --- | --- |
| `--create` | 直接创建快捷方式（不进入图形界面） |
| `--delete` | 按参数定位并删除**已存在**的快捷方式（检测到存在才删） |
| `--location` | `desktop` / `publicdesktop` / `startmenu` / `allusersstartmenu` / `custom` |
| `--custom-dir` | 自定义目录（填了就优先于 `--location`） |
| `--target` | 目标程序，默认自动探测 `iexplore.exe` |
| `--args` | 启动参数，默认 `https://www.baidu.com/#ie= -Embedding` |
| `--name` | 快捷方式名称，默认 `IE` |
| `--safe-name` | 名字含 `Internet Explorer` 时改用不含该字样的安全名（避免被系统刷新成旧版 IE 条目） |
| `--icon` | `system`（用 IE 程序自带图标，默认）/ `bundled`（用工具内置图标） |
| `--json` | 以 JSON 输出结果（含逐项核对明细），便于脚本消费 |
| `--test` | 创建后立即测试启动并判定结果 |
| `--fallback-startmenu` | 创建位置被安全软件拦截时，自动改存到“开始菜单”重试 |

> 含空格的参数务必加引号：cmd / PowerShell 均需 `--name "Internet Explorer"`。
> 退出码：`0` 全部核对通过，`1` 创建失败，`2` 创建成功但有参数没写进去。
> 输出到管道 / 文件时统一使用 **UTF-8**（不依赖系统代码页）；直接连控制台时用控制台自身编码，中文显示正常。

## 删除快捷方式：先检测，存在才删

“删除快捷方式”不再只认“本次会话刚创建出来的那个”，而是**按界面上的参数去检测**：

- 检测范围 = 界面上的「创建位置 + 快捷方式名」算出的路径，**加上**同一个名字的变体
  （`X.lnk` / `X (IE).lnk` / `X 快捷方式.lnk`），**再加上**本次会话刚创建的那个路径；
- **候选名只由界面上填的名字派生**：不会把无关的名字混进检测范围。
  （早期版本候选里硬塞了 `IE 快捷方式.lnk` / `IE.lnk`，于是 `--delete --name ZZZ不存在`
  反而把同目录的 `IE.lnk` 删掉了——2026-11-16 实测发现并修复，已有
  `tests/test_delete_scope.py` 盯着这个行为。）
  唯一的例外是界面名字**本身含 `Internet Explorer`** 时：那种情况下系统会改写、
  工具会另存成 IE 类安全名，所以 `IE 快捷方式.lnk` / `IE.lnk` 仍在检测范围内；
- **检测到已存在才执行删除**，并且删完会复核文件是否真的没了；
- 一个都没检测到时，会明确告诉你“会检查哪些位置”，而不是一句“当前没有可删除的快捷方式”；
- 删除前弹窗列出**将要删除的完整路径**让你确认；
- **系统自带的 IE 条目**（指向 iexplore.exe 且没有参数的那个）默认跳过不删，避免把系统的 IE 入口删掉，会在结果里说明。

命令行同样支持：

```bat
ie_launcher.exe --delete --location startmenu --name "IE 快捷方式"
```

检测不到时返回 `1`，删成功返回 `0`，部分失败返回 `2`。

## 实测结论

在 Windows 10 22H2（19045）上实测：

1. **`-Embedding` 是关键**。带 `-Embedding` 时 `iexplore.exe` 会启动真正的 IE（窗口类 `IEFrame`，标题形如“百度一下，你就知道 - Internet Explorer”）；
   去掉它，同样的程序会被 Microsoft Edge 接管（`msedge.exe --from-ie-to-edge=8`）。
2. **URL 不能加引号**。写成 `"https://www.baidu.com/#ie="` 会导致 IE 报“无法访问此页面”。
3. **参数顺序有讲究**：URL 在前、`-Embedding` 在后最稳；把开关放前面能开 IE，但页面不会加载。
4. **64 位与 32 位启动器都可用**：重复测试 64 位 6/6、32 位 4/4 全部打开真 IE；界面提供“用 32 位 IE”一键切换。
5. **Windows 11 没有 IE 桌面程序**（`iexplore.exe` 不存在），只能用 Edge 的 IE 模式：
   `edge://settings/defaultBrowser` → 把目标站点加入“Internet Explorer 模式页面”。界面里有“一键跳转”按钮。
6. IE11 桌面程序被 Edge 更新停用后，系统目录仍保留 `mshtml.dll` 等组件，Edge 的 IE 模式正是靠它实现。

## 安全软件拦截与三级兜底

部分国产安全软件（实测本机为腾讯电脑管家 + McAfee）会拦截“在桌面新建快捷方式”，实测规则（2026-11-16 复测）：

- **当前用户桌面禁止创建任何 `.lnk`**：用原始字节直接写也一样被拒，且**与文件名、目标程序、图标都无关**——
  指向 `notepad.exe` 的 `记事本目标.lnk`、指向 `iexplore.exe` 的各种名字，实测全部 `Permission denied`；
  同样的文件写进开始菜单则全部成功。**这是按目录拦的，不是启发式误报，改快捷方式本身的属性绕不过去。**
- 拦截是**间歇性**的：同一台机器上反复测试，有时放行、有时拒绝，还会把已存在的快捷方式删掉。
  实测记录：09:3x 与 10:1x 被拒，**10:36 用同一个 exe 又一次直接放行**（7 项核对全 √，方法 pywin32）。
- **所有用户桌面**（`C:\Users\Public\Desktop`）需要管理员权限，且 COM 新建也可能被拒，需要走下面的兜底。
- **创建成功 ≠ 长期存在**：杀软会在几分钟后的某个时刻把之前建好的 `.lnk` 清掉（10:2x 建好的三份，10:3x 就全没了）。
  这是杀软策略随时间变化造成的，工具层面无法保证不被删；界面会如实报告"创建成功"，但不承诺"永远在"。

工具因此内置三级兜底，逐级尝试并把实际使用的方式写进日志：

1. 直接用 `WScript.Shell` 在目标位置创建（最快，字段最全，也是最“系统原生”的一种）；
2. 换 PowerShell 再试一次（若上一次是“拒绝访问”，同一 COM 引擎必然同样失败，直接跳过以免白等）；
3. **临时目录让 Windows 生成一份 `.lnk`，再把它的原始字节搬到目标目录**。
   搬运分两步试：先按**最终文件名**直接写字节（绕开“复制后改名”里被拦的改名动作），
   写不进去再退回“复制成临时名 + 改名”。若文件名本身被拦，自动改用
   `IE (IE).lnk` / `IE 快捷方式.lnk` 等备选，并在日志里说明原因。

> **为什么不用“自己拼 .lnk 二进制”那条路**：MS-SHLLINK 里 Windows 解析目标路径主要依赖
> `LinkTargetIDList`（外壳 ID 列表），手工拼的 `LinkInfo` 缺 IDList 时系统会退回去读
> `RelativePath`，结果就是**图标能显示、目标却是空的**——快捷方式建得出来、点不动。
> 这条坑本项目踩过一次（老版本叫“二进制直写”），现已整体删除：
> 落盘内容一律由 Windows 自己生成，格式与系统完全一致。

遇到“拒绝访问”时会直接跳到下一级并逐条写进日志，所以日志里看到哪一级成功，就能确认前面几级分别被什么挡住了。

工具不会绕过系统的安全策略去做别的事，只是换一条被允许的写入路径把快捷方式建出来；如果你要保留原名，请在安全软件里放行，或把创建位置改成开始菜单。

## 系统会刷新“Internet Explorer”开头的快捷方式

实测本机规则：**在系统托管的位置，名字含 “Internet Explorer” 的快捷方式会被系统改写成旧版 IE**（目标变成 32 位 `IEXPLORE.EXE`、参数被清空）。这不是本工具写错——改写前后重新读回就能发现内容被换掉了。

实测范围（2026-11-16 逐项复测）：

| 位置 | 是否被改写 |
| --- | --- |
| 当前用户开始菜单 | 会 |
| 所有用户开始菜单 | 会 |
| **所有用户桌面** | **会** |
| 当前用户桌面 | 同一套外壳规则 |
| **自定义目录 / 其它普通目录** | **不会** |

实测细节：

- 触发条件是**名字里含 “Internet Explorer” 这个子串**：`Internet Explorer`、`Internet Explorer (IE)`、
  `Internet Explorer 网页`、`我的 Internet Explorer` 在开始菜单里都会被改写；
  `IE 快捷方式`、`IE`（不含空格的那个子串）不会；
- **与创建方式无关**：原生 `WScript.Shell` 直接创建、原始字节搬运、属性归一化后再搬运——三种方式实测都在 3 秒内被改写；
- 改写很快（实测 **1.7 秒内**完成），所以“建完立刻读回”发现不了，必须过一会儿再复核；
- 同样内容存到**非系统托管的目录**（自定义目录等）则完全正常。

工具的对策（**不擅自改名**）：

- **默认名称用 `IE`**，不含那个子串，因此在开始菜单 / 桌面上不会被系统刷新；
- 你在界面里填什么名字就用什么名字，工具不做任何自动改名；
- 创建完成后**延迟 2 秒复核**：一旦发现被系统改写，**如实上报**并弹窗询问是否换个名字重建（命令行可用 `--safe-name` 直接换）；
- 预览区在系统托管位置 + 名字含该子串时，会提前给出提醒；
- 目标位置已经存在**系统自带**的 `Internet Explorer` 条目时，不去覆盖它，而是另存新名并提示，避免被系统还原。

想让名字原样保留又要有功能，**把“创建位置”改成自定义目录**即可（实测非系统托管的目录不会被改写）。

## “所有用户桌面”需要管理员权限

`所有用户桌面` / `所有用户开始菜单` 普通权限写不进去。工具的处理：

- 图形界面：创建失败时弹窗询问**是否以管理员身份重新运行**，确认后自动提权重启，并把界面上填的全部参数原样带过去，不会丢；
- 命令行：报错文案会直接说明需要管理员权限；
- 预览区在选中这两个位置时会给出提示。

## 实测：默认名 `IE` 的完整验收

2026-11-16 用默认参数（名称 `IE`）在三处实测（Windows 10 22H2）：

| 位置 | 落盘文件 | 写入方式 | 7 项核对 | 被系统刷新 |
| --- | --- | --- | --- | --- |
| 当前用户开始菜单 | `…\Start Menu\Programs\IE.lnk` | pywin32 | 全部 `√` | 否 |
| 当前用户桌面 | `D:\23952\Desktop\IE.lnk` | pywin32 | 全部 `√` | 否 |
| 所有用户桌面（管理员） | `C:\Users\Public\Desktop\IE.lnk` | pywin32 | 全部 `√` | 否 |

三个文件的"系统默认属性"核对一致：

```
外部 mtime == ctime == 创建时刻      属性 0x20 (ARCHIVE)
内嵌 ShellLink 时间戳 = iexplore.exe 的时间戳（外壳写入，不改动）
内容含 baidu 与 -Embedding
```

模拟双击 `IE.lnk`：弹出真正的 IE 窗口，窗口标题为「百度一下，你就知道 - Internet Explorer」——
说明 `-Embedding` 生效、页面也加载了，不是 Edge 接管、也不是旧版 IE。

### 存活实验：谁会被杀软删掉

同一时刻在开始菜单里放 5 个 `.lnk`（工具建 2 个 + 手工对照 3 个），每 10 秒轮询一次，连看 **15 分钟（900 秒）**：

| 快捷方式 | 来源 | 结果 |
| --- | --- | --- |
| `IE.lnk` | 工具创建（64 位 IE + `-Embedding`） | 存活 900 秒 |
| `IE 网页.lnk` | 工具创建，同目标不同名 | 存活 900 秒 |
| `记事本测试.lnk` | 手工 `WScript.Shell`，目标是记事本 | 存活 900 秒 |
| `IE 无参数.lnk` | 手工 `WScript.Shell`，目标是 IE、无参数 | 存活 900 秒 |
| `IE 32位.lnk` | 手工 `WScript.Shell`，32 位 IE + `-Embedding` | 存活 900 秒 |

也就是说：**只要落盘成功，文件本身不会被立刻清掉**。之前"三处一起消失"是建好**几分钟之后**被杀软的
定时/延迟清理带走的（10:2x 建好 → 10:3x 全没了），不是工具写出的文件有特征问题。



## 重新打包

```bat
.venv\Scripts\python -m PyInstaller --clean --noconfirm ie_launcher.spec
```

`.venv` 是用 uv 基于 `D:\ProgramData\anaconda3\python.exe` 创建的隔离环境，只装了 `pyinstaller` 与 `pywin32`，
不会影响系统里的 Anaconda base 环境。

打包会带上 `ie_launcher.manifest`（清单里声明 `PerMonitorV2` 的 DPI 感知）——
**去掉它也能跑**，代码里会在建窗口前自己调 `SetProcessDpiAwarenessContext`；
留着的好处是进程从启动起就是 DPI 感知，连命令行模式弹的提示框也是清晰的。

## 已知限制

- 图形界面是 tkinter，缩放适配做到了“清晰 + 不重叠 + 整窗可见”，但**布局不会自动重排**：
  界面是固定结构的，缩放比例变化时按同一系数等比缩放，不会换成更紧凑的排版。
  （低分辨率下会切到紧凑版，见上文“低分辨率屏幕适配”。）
- `--location publicdesktop` / `allusersstartmenu` 需要管理员权限写入；界面会提示并可一键提权重试，命令行需自行以管理员身份运行。
- Edge 的 IE 模式是微软的兼容方案，官方声明至少支持到 2029 年；IE 桌面程序已停止支持（2022-06-15）。
- 落盘内容一律由 Windows 自己生成，因此“描述”等字段都完整；但如果系统把快捷方式改写了，
  工具只能在改名范围内自愈，无法阻止系统对特定名字的改写（这也是要避开 “Internet Explorer” 这个名字的原因）。
- **安全软件是按“目录”拦的，不是按快捷方式内容拦的**：本机腾讯电脑管家 + McAfee 会拒绝在
  当前用户桌面写入任何 `.lnk`（连指向 `notepad.exe` 的也一样），而同样的内容写开始菜单全部成功。
  这属于本机安全策略，改快捷方式属性、换图标、换目标程序都绕不过去。遇到这种情况请
  ① 把“创建位置”改成**开始菜单**（实测 100% 可写），或 ② 在安全软件里对桌面目录放行。
  拦截还是间歇性的（同一台机器有时放行、有时拒绝，还会顺手删掉已存在的快捷方式），
  如果创建失败请过几秒重试一次。
- **名字含 “Internet Explorer” 又放在系统托管位置（开始菜单 / 桌面）时会被系统改写**，
  表现为目标被换成 32 位 `IEXPLORE.EXE`、参数被清空。想让名字原样保留又要有功能，
  把“创建位置”选成**自定义目录**（实测非系统托管目录不会被改写）；用默认名 `IE` 则在任何位置都安全。
- **exe 是 GUI 子系统程序（不弹控制台）**，所以在 PowerShell 里直接 `& ...\ie_launcher.exe --create` 会**立刻返回、
  拿不到退出码**；要等它跑完请用 `Start-Process -Wait -PassThru` 或 `cmd /c ie_launcher.exe --create ...`。
  输出重定向到文件时固定 UTF-8（`cmd` 用 `>` 重定向即可）；在控制台里则跟随控制台代码页。
- 屏幕特别小（比如 640×480）且系统缩放很高时，界面会缩到 62%（相对 96 DPI 基准）才放得下，
  这时字号会明显偏小——这是“保证整窗可见”的取舍；放不下的部分可以用滚动条访问。
